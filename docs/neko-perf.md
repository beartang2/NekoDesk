# 네코데스크 CPU 측정 (1단계: 재기만)

2026-11-18, `neko-v26` dc9188d 를 릴리스 빌드로 쟀다. 코드는 고치지 않았다. 고칠 방법과 담당은 §3 에 제안만 적는다.

## 1. 한눈에

- 메인 창이 보이고 네코가 **방(사이드바)** 에 있으면 앱 전체가 **한 코어의 15–23%** 를 쓴다. 이 중 **10–15 는 앱 안 네코 엔진**이 화면 주사율(60Hz) 그대로 매 프레임 다시 그리는 값이다.
- **대화 스트리밍** 중에는 **40–52%** 까지 오른다. 토큰마다 답 전체를 다시 그리기 때문이다.
- **마당(모니터 화면)** 은 30fps 에서 14–17%, 60fps 에서 17–21% 다. 기본값은 60fps 다.
- 메인 창을 **숨기거나(⌘H) 다른 Space·전체화면 앱 뒤로 가면 1% 안팎**이다. 이 경우는 이미 잘 쉰다.
- 오로라·햇빛 CSS 애니메이션, 1초 타이머, '다른 앱 따라 하기' 폴링은 모두 1–2% 이하라 우선순위가 낮다.

## 4. 어떻게 쟀나

- **빌드**: 릴리스(`tauri build --no-bundle`, dc9188d) 측정용 임시 복사본. 사용자 데이터·dev 앱과 섞이지 않게 아래처럼 바꿨고, 커밋하지 않았으며 측정 뒤 모두 지웠다.
  - identifier, 키체인 서비스 이름, 실행 파일 이름을 따로 썼다. `secrets.rs` 의 `SERVICE` 가 고정값이라, 바꾸지 않으면 진짜 DB 열쇠를 읽으려 한다.
  - ⌃⇧N 등록과 업데이트 확인을 껐다.
  - 창은 1100×720 이고, 실행 4 에서는 전체화면 앱 위에도 보이는 패널로 띄웠다.
  - 상태를 30초씩 차례로 바꾸는 드라이버를 붙였다.
- **수치**: 1초마다 `ps -axo pid,ppid,time,comm` 로 누적 CPU 시간을 읽고 그 차이를 평균했다. 상태마다 앞 6초와 끝 1초는 뺐다.
  - 앱의 WebKit 프로세스는 '책임 프로세스'로 가렸다.
  - 앱을 그냥 띄우면 책임자가 VS Code 가 되어 dev 앱의 WebKit 과 섞인다. 그래서 책임을 넘기지 않게(disclaim) 띄웠다.
- **창이 안 보이던 초는 뺐다.** 측정 중 창이 다른 Space·전체화면 앱 뒤에 있던 동안은 WebKit 이 그리지 않아 수치가 1% 로 떨어졌다.
  - 실행 3·4: `CGWindowListCopyWindowInfo`(화면에 있는 창)로 보고 뺐다.
  - 실행 1·2: 엔진이 도는 상태만, 메인 웹뷰 + GPU 가 1.5% 미만인 초를 뺐다. 실행 3 은 거의 다 안 보여 마당·숨김만 썼다.
- **스트리밍은 모의**다. `messageStore` 에 33ms 마다 6자(초당 약 180자, 굵은 글씨·목록·코드 블록 섞음)를 붙였다.
  - `isRunning` 이 아니어서 '생각 중' 표시와 감독 반응은 빠졌다.
  - 실제 스트리밍은 토큰마다 갱신하므로 이보다 잦다.
- **환경**: M4(10코어), 화면 2개 모두 60Hz. 사용자는 측정 중에도 다른 앱을 쓰고 있었다.
- **WindowServer** 는 시스템 전체 값이라 다른 앱 소음이 크다(15–45%). 앱이 보이며 움직일 때가 숨겼을 때보다 대략 5–15 높았지만 깔끔히 가르지 못했다.
- **dev 빌드**는 따로 재지 않았다. 참고로 사용자의 dev 앱을 상태를 모른 채 30초 재 보니 GPU 20%, 웹뷰 7.7%, 본체 5.9% 였다. React 개발 모드라 릴리스보다 무거울 수 있다. 사용자가 본 CPU 가 dev 앱이었다면 이 표보다 높게 보였을 것이다.
- **한계**: 엔진 비용은 고양이가 무엇을 하느냐에 따라 ±4 흔들린다. 상태마다 약 22초라 2점 미만 차이는 가려내지 못한다.

### 5.1 화면 쪽(스트리밍 묶기·문단 memo, 빛줄기·오로라) — 45c2af2

2026-11-19. 고치기 전은 바로 앞 커밋 f6c5d17, 고친 뒤는 45c2af2 다. 둘 다 릴리스 빌드이고, 번갈아 2번씩(실행 2·4 와 1·3) 쟀다. 상태마다 22초 × 2번이다.

- **스트리밍은 이번엔 진짜 길로 쟀다.** 측정용 가짜 OpenAI 호환 서버(127.0.0.1)에 붙였고, 입력창에서 보내면 `useAgentLoop` 의 `streaming_token` 을 그대로 지난다. 그래서 1단계의 모의(메시지 저장소에 직접 붙이기)와는 숫자를 바로 견주지 않는다.

- **스트리밍**: 30Hz 는 −19.5(−36%), 빠르게는 −77(−68%)이다. 메인 웹뷰가 32 → 16, 83 → 16 으로 줄었다. 고치기 전엔 글이 빠를수록, 답이 길수록 커졌는데, 고친 뒤엔 속도와 상관없이 16 근처다. 화면을 66ms 마다 한 번 고치고, 끝난 문단은 다시 해석하지 않는다.
- **오로라·빛줄기 멈춤**은 방에서 따로 보이지 않았다. 창 비활성(멈춤)이 창 활성보다 오히려 높게 나왔는데, 1단계에서 잰 ≈ 1.5 가 엔진 흔들림(±4)에 묻힌 것이다. 빛줄기 blur 고정도 같다. 셋 다 고친 뒤 방 평균이 전보다 낮게 나왔지만(24.6 대 30.4), 이번 변경과 상관없는 엔진 흔들림이 섞여 있어 이 차이를 효과로 보지 않는다.

### 5.2 마당(화면 창·Rust·기본값) + 엔진 프레임 정책 — f6c5d17 + cdfbe0b

2026-11-19. 고치기 전은 e1a866a(마당·엔진·화면 쪽 셋 다 전), 고친 뒤는 cdfbe0b(마당 f6c5d17·화면 쪽 45c2af2·엔진 cdfbe0b 다 들어감)다. 릴리스 빌드, 같은 방법(§4, 디자이너 스크립트 그대로)으로 번갈아 3번씩(전 2·4·6, 후 1·3·5) 쟀다. 상태마다 22초 × 3번. 표는 3번의 **가운데 값**이고, 합계 옆 괄호는 가장 낮은·높은 값이다.

- **이번 측정은 흔들림이 크다.** 측정하는 동안 사용자가 맥을 쓰고 있었다(모니터 3대, Space·화면 잠김). 메인 창이 가려진 실행(전 4 의 방 1.4, 후 3 의 숨김 1.6)처럼 0 에 가깝게 떨어진 값이 섞였다. 그래서 평균 대신 가운데 값을 쓰고, 5 넘게 차이 난 것만 효과로 본다.
- 1단계 표(dc9188d)보다 전반적으로 높다. 모니터 3대에 마당 선물 창이 모니터마다 뜨고(83f91f6), 측정 날이 다르다. 같은 실행 안 전·후로만 본다.
- 마당 기본값이 30 으로 바뀌어서 사용자가 실제로 보는 것은 '전 마당 60' → '후 마당 30' 이다: **27.0 → 23.9**.

- **앱 본체(Rust)가 마당에서 반쯤 줄었다(7.9 → 3.8).** 커서가 고양이·선물에서 멀면 폴러가 10Hz 로만 읽고 화면 창에 커서를 안 보낸다. 측정 중 커서는 대부분 고양이에서 멀었다(사용자가 다른 일을 했다).
- **메인 웹뷰가 마당에서 3 → 0.2.** 마당일 때 멈춘 앱 안 엔진이 rAF 를 더 안 건다(엔진 cdfbe0b, §3 2번).

- **마당 60 은 줄지 않았다(오히려 +4, 흔들림 안).** 같은 60fps 라 화면 창이 하는 일은 같고, 엔진 상한이 rAF 를 거르는 대신 setTimeout 뒤 rAF 로 바뀌면서 60 을 더 꽉 채워 그리는 것으로 보인다(추정). 기본값을 30 으로 내린 게 이 줄의 대책이다.
- **'항상 위' 끔은 표에서 뺐다.** 끄면 고양이가 다른 창 아래라, 창에 가려진 실행에선 WebKit 이 그리지 않아 0–29 로 흩어졌다. 캣타워(창 목록 읽기) 비용은 앞에 적은 미세 측정(다 읽기 0.16ms·창 하나 0.06ms, 1% 미만)으로 갈음한다 — 이 흔들림 안에서 가려낼 수 없다.
- **방·거실·방 졸 때는 이번 측정으로는 효과가 안 보인다**(엔진 30fps 상한, ±3 안). 산책 중은 −15 로 뚜렷하다(멈춘 엔진 rAF). 엔진 쪽 해석은 집사가 붙인다.
- 화면 쪽 오로라 멈춤(45c2af2)도 '후' 빌드에 들어 있다. 방 숫자엔 그것도 섞여 있다(§5.1 에선 흔들림 안).
