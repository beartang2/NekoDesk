## 0. Settled Scope (2026-08)

> 아래 1–21번 섹션은 TUI 시절에 쓴 계획 문서다. 충돌하는 서술이 있으면 **이 섹션이 우선**한다.
> 여기 적힌 항목은 대부분 이미 코드에 반영되어 있다.

### 플랫폼

- 터미널 TUI/CLI는 폐기됐다. Tauri 2 + React 19 + TypeScript 데스크톱 앱이 유일한 형태다. ✅ 완료
- Node 서비스 계층과 FastAPI 프록시는 없어졌다. LLM·저장소·도구 호출은 전부 앱 내부(Rust command + 프론트 IPC)에서 처리한다. ✅ 완료
- llama-server 라이프사이클은 앱이 직접 관리한다(기동/종료/고아 청소). ✅ 완료

### 기능 스코프

초기 계획의 4개 기능 중 남길 것과 뺄 것.

| 기능 | 결정 | 상태 |
|------|------|------|
| ToDo 리스트 | 유지 | ✅ `todo.*` 도구 + TodoCard |
| 일정 관리 | **캘린더 기록 형태로 변경** | ✅ `schedule.*` 도구 + CalendarCard(월 그리드) |
| 메모 | **제거** | ✅ 코드에서 제거됨 |

| 기능 | 상태 |
|------|------|

| 날씨 | ✅ `weather.get` |

## 1. Reading Summary

### 프로젝트 핵심 해석

- NekoDesk의 본질은 "CLI 생산성 도구"보다 "터미널 안에서 함께 일하는 고양이 동반자"에 가깝다.
- 차별점은 감성 요소 자체보다, 감성이 실제 기능 흐름과 연결되어 있다는 점이다.
- 메모, 할 일, 일정, GitHub, 웹 검색이 전부 자연어 인터페이스로 이어지는 것이 제품 경험의 중심이다.
- 한국어 우선, 로컬 LLM, 프라이버시 지향은 취향이 아니라 제품 정체성에 가깝다.

### 현재 문서에서 보이는 강점

- 제품 비전이 선명하다.
- UI, 아키텍처, 저장소, 테스트까지 큰 그림이 연결되어 있다.
- "왜 이 프로젝트를 만들었는가"가 기능 목록보다 더 잘 드러난다.

### 현재 문서에서 보이는 긴장 지점

- 감성 중심 제품과 생산성 도구로서의 신뢰성 사이의 균형
- 로컬 LLM 기반 자연어 UX와 결정론적 동작 사이의 균형
- 터미널 경험의 매력과 복잡성 증가 사이의 균형
- 기능 확장 속도와 컨텍스트 비용/품질 통제 사이의 균형

> 메모: CLI 플랫폼을 버리고 앱 형태로 만들 예정.
>       마스코트 캐릭터는 픽셀아트의 고양이. 레퍼런스는 내가 이미지 3장정도 첨부할 것임.
>       이걸 픽셀아트로 애니메이션화해서 아기자기하게 만들어줘야 함.

## 2. Verified Facts vs. Assumptions

### 현재 코드에서 확인된 사실

- 브랜치는 `app-dev` 기준이다.
- `web-search-client.js`와 `tests/web-search-client.test.js`는 아직 untracked 상태다.
- 대화 메모리는 별도 저장소와 메모리 상태를 함께 쓰고 있다.
- `llm.historyLimit` 기본값은 현재 코드상 `12`다.
- 웹 검색 후처리는 기사 본문이 아니라 제한된 검색 결과 구조를 기반으로 한다.

### 검증이 필요한 항목

- `research.md`에 적힌 인텐트 이름과 현재 실제 인텐트 이름이 완전히 일치하는가
- 설정 키 이름 설명이 현재 코드와 정확히 맞는가
- "현재 상태와 미완성 부분" 서술이 지금 워크트리 기준으로도 유효한가
- LLM 3단계 구조 설명이 현재 최신 코드 흐름을 충분히 반영하는가

### 이 문서에서 지킬 원칙

- 검증된 사실과 해석을 분리해서 적는다.
- 이후 실행 계획은 "현재 코드 기준"으로만 확정한다.
- `research.md`의 비전은 유지하되, 세부 구현은 최신 코드에 맞춰 조정한다.

## 3. Planning Frame

### 지금 이 계획 문서가 답해야 하는 질문

1. NekoDesk를 다음 단계에서 무엇으로 더 선명하게 만들 것인가
2. 지금 손봐야 할 것은 기능 확장인가, 구조 안정화인가, UX 정교화인가
3. 감성 요소와 신뢰성 요소 중 어느 축의 완성도를 먼저 끌어올릴 것인가
4. 웹 검색, GitHub, 대화 컨텍스트 같은 최근 변화 중 무엇을 우선 정리할 것인가

### 우선순위 판단 기준

- 제품 정체성을 더 선명하게 만드는가
- 실제 사용 빈도가 높은 흐름을 개선하는가
- 로컬/프라이버시 철학을 해치지 않는가
- 구현 복잡도 대비 체감 가치가 큰가
- 테스트 가능하고 회귀 위험을 통제할 수 있는가

## 4. Goals

### Primary Goals

- 고양이 동반자 경험과 생산성 도구 경험이 따로 놀지 않게 정리한다.
- 자연어 입력에서의 예측 가능성과 신뢰성을 높인다.
- 최근 추가된 웹 검색 경로를 제품 톤과 기술 제약 안에서 안정화한다.
- UI, 상태, 컨텍스트 관리에서 장기적으로 발목 잡을 부분을 조기에 정리한다.

### Secondary Goals

- 한국어 UX의 일관성을 더 높인다.
- 사용자가 "어떻게 말해야 하는지" 학습하지 않아도 되게 만든다.
- 테스트가 제품 설계 의도를 더 잘 설명하도록 만든다.

### Non-Goals

- 단기적으로 기능 수를 무작정 늘리는 것
- 클라우드 의존 기능을 전제로 구조를 다시 짜는 것
- 시각적 연출만 늘리고 실제 사용 흐름은 그대로 두는 것

## 5. Candidate Workstreams

### Workstream A. Product Identity

- "터미널 동반자" 경험을 더 선명하게 만드는 규칙 정리
- 감성 표현이 기능 신뢰성을 해치지 않도록 톤 가드레일 정리
- 도움말, 기본 문구, 실패 메시지의 제품 톤 통일

### Workstream B. LLM and Context Reliability

- 인텐트 분류, tool planning, chat 응답의 경계를 더 명확히 정리
- 대화 히스토리와 툴 결과 주입 방식의 비용/예측 가능성 점검
- 웹 검색 후처리에서 LLM 사용 범위를 어디까지 허용할지 결정

### Workstream C. Terminal UX

- 채팅 뷰, 리스트 뷰, 확인 다이얼로그 흐름의 일관성 점검
- 키보드 중심 사용성 강화
- 작은 터미널 크기에서의 정보 밀도와 피로도 조정

### Workstream D. Data and Persistence

- 메모, 할 일, 일정, 대화 이력의 저장 규칙과 표시 규칙 분리
- in-memory state와 persisted state의 책임 경계 재정리
- 복구/재시작 시 사용자 기대와 실제 동작 차이 점검

### Workstream E. Quality and Test Strategy

- 최근 추가된 기능에 대한 회귀 테스트 보강
- 설계상 중요한 불변식을 테스트로 고정
- 제품 톤/대화 정책을 어디까지 테스트할지 기준 수립

> 메모: 감정에 따라 행동 애니메이션 등이 달라질 수 있도록.

## 21. Conversation Sessions and Runtime Controls

### 새로 필요한 기능

- 새 대화 세션 생성
- 세션 히스토리 목록 탐색
- 세션 이름 자동 생성 또는 수동 변경
- 응답 생성 중 `Stop` 버튼
- 모델 미기동 시 앱 시작과 함께 자동 기동
- 앱 종료 시 모델 자동 종료

### 세션 UX 방향

- 세션은 좌측 rail에서 목록으로 본다.
- 최근 세션, 고정 세션, 즐겨찾기 정도로 나누는 방식이 좋다.
- 현재 세션 제목은 상단 바에 간단히 노출한다.
- 새 대화 버튼은 항상 눈에 띄어야 한다.

### 응답 중단 기능

- 사용자가 긴 응답을 중단할 수 있어야 한다.
- stop은 composer 주변이나 메인 채팅 하단에 명확한 버튼으로 둔다.
- 중단된 응답은 "partial answer" 상태로 세션에 남길지 결정이 필요하다.

### 모델 라이프사이클

- 앱 시작 시 모델 상태를 먼저 확인한다.
- 모델이 꺼져 있으면 자동 기동을 시도한다.
- 모델 준비 전에는 입력창을 disabled 하거나 준비중 상태를 명확히 보여준다.
- 앱 종료 시 사용자가 원하면 모델도 함께 내린다.

### FastAPI 레이어 재검토

- FastAPI가 단순 프록시 역할이라면 제거 후보로 본다.
- 가능하면 데스크톱 앱 내부 런타임에서 LLM 호출과 GitHub 호출을 직접 처리하는 구조가 더 단순할 수 있다.
- 단, Python 레이어가 실제로 꼭 필요한 기능을 담당한다면 유지한다.
- 이 항목은 마이그레이션 초기에 반드시 판단해야 한다.

## 8. Risks

- 제품 정체성은 좋은데 우선순위가 넓어져 실행력이 떨어질 수 있다.
- 자연어 UX를 넓힐수록 예측 가능성이 낮아질 수 있다.
- 감성 요소가 많아질수록 실패 상황에서 신뢰를 잃을 수 있다.
- 웹 검색과 컨텍스트 처리 방식이 장기적으로 품질 변동성을 키울 수 있다.
- 문서가 코드보다 앞서 달리면 팀의 공통 이해가 다시 흐려질 수 있다.

## 11. Desktop App Direction

### 목표

- 기존 TUI의 정체성은 유지하되, 데스크톱 앱답게 더 안정적이고 여유 있는 레이아웃으로 재구성한다.
- 다른 에이전트 앱들과 비슷하게 "사이드바 + 메인 대화 + 보조 패널" 구조를 가져가되, 고양이 펫을 전면적인 차별점으로 둔다.
- 고양이는 단순 마스코트가 아니라 상태, 감정, 작업 진행, 대화 분위기에 반응하는 인터랙션 레이어가 된다.

### 추천 방향

- 제품 방향만 보면 `Tauri + React + TypeScript`가 가장 잘 맞는다.
- 현재 코드 재사용성과 전환 속도만 보면 `Electron + React + TypeScript`가 가장 현실적이다.
- 지금 코드베이스가 Node 중심 오케스트레이션을 이미 갖고 있으므로, 빠르게 옮기려면 Electron이 유리하다.
- 앱 크기, 보안 기본값, 장기 배포 관점까지 고려하면 Tauri가 더 매력적이다.

### 추천안 A. 빠른 전환

- Shell: Electron
- UI: React + TypeScript + Vite
- 상태관리: Zustand
- 서버 상태/비동기 캐시: TanStack Query
- 스타일: Tailwind CSS 또는 CSS Modules + design tokens
- 애니메이션: Motion
- 로컬 저장소: 현재 SQLite 계층 최대 재사용
- 브리지: preload + `contextBridge` + 좁은 IPC surface

### 추천안 B. 장기 지향

- Shell: Tauri 2
- UI: React + TypeScript + Vite
- 상태관리: Zustand
- 서버 상태/비동기 캐시: TanStack Query
- 스타일: Tailwind CSS 또는 CSS Modules + design tokens
- 애니메이션: Motion + Canvas 기반 펫 렌더링
- 로컬 저장소: SQLite 유지
- 시스템 통합: Tauri command/event 기반

### 내 권장

- 지금은 Electron으로 먼저 옮기고, 제품 구조가 자리 잡은 뒤 필요하면 Tauri를 검토하는 쪽이 더 현실적이다.
- 이유는 현재 `app-controller.js`와 서비스 계층이 Electron main process와 자연스럽게 맞물리기 때문이다.
- 반대로 처음부터 Tauri로 가면 앱 쉘은 좋아지지만 오케스트레이션 레이어를 다시 정리해야 할 가능성이 높다.

## 13. Cat System For Desktop

### 역할

- 상태 표시기
- 감정 표현기
- 작업 진행 피드백 장치
- 앱의 기억점이 되는 시그니처 요소

### 구현 방향

- 펫은 `픽셀아트 기반`으로 구현한다.
- 렌더링은 `스프라이트 시트 또는 프레임 시퀀스 + 상태 머신`을 기본으로 한다.
- 초기에 본 리깅이나 복잡한 파츠 시스템으로 가지 않는다.

### 스타일 원칙

- 형태는 단순하고 둥글게 유지한다.
- 표정은 최소 요소로 읽히게 만든다.
- 움직임은 과하지 않게, 짧고 반복 가능한 루프로 설계한다.
- 배경 연출은 보조적이어야 하며, 펫보다 더 눈에 띄면 안 된다.
- 전체 앱 레이아웃은 깔끔하게 유지하고, 픽셀아트는 펫 영역 중심으로만 사용한다.

### 상태 설계

- 감정 상태와 행동 상태를 분리해서 설계한다.
- emotion 예시: `idle`, `happy`, `curious`, `sleepy`, `error`
- action 예시: `blink`, `lookAround`, `walkIn`, `typing`, `celebrate`, `fail`

### 제작 원칙

- 먼저 작은 해상도의 기본 포즈 세트를 만든다.
- 이후 상태별 파생 프레임을 늘리는 방식으로 확장한다.
- 색상 변형보다 포즈와 타이밍 차이로 감정을 구분하는 쪽을 우선한다.
- 구현 1차 목표는 "부드러운 고급 애니메이션"보다 "읽기 쉽고 안정적인 반응"이다.

### 입력 레퍼런스

- 정면 / 측면 / 앉음 / 걷기 / 타이핑 / 기쁨 / 당황 / 졸림 정도의 기준 이미지가 있으면 충분하다.
- 배경 투명 PNG 시퀀스나 픽셀 단위 프레임 샘플이 있으면 구현 자유도가 높다.

### 초기 제작 단위 제안

- base idle
- idle blink
- typing
- curious look
- happy bounce
- sleepy doze
- error freeze

## 16. Visual Style Guide

### 목표 톤

- 전체 제품은 깔끔하고 현대적인 에이전트 앱처럼 보이되, 지나치게 차갑지 않아야 한다.
- 고양이 펫은 분명히 귀엽고 살아 있어야 하지만, 앱 전체가 장난감처럼 보이면 안 된다.
- 결과적으로 "업무용 도구"와 "작은 동반자"가 동시에 느껴지는 방향을 유지한다.

### 핵심 무드 키워드

- calm
- tidy
- warm
- companion-like
- playful in a controlled way

### UI 스타일 원칙

- 화면 구조는 단순하고 정돈된 그리드를 사용한다.
- 패널 구분은 강한 테두리보다 여백, 밝기 차이, 얕은 그림자로 해결한다.
- 채팅 영역은 가독성이 최우선이어야 한다.
- 오른쪽 컨텍스트 패널은 정보 카드 중심으로 구성한다.
- 좌측 펫 영역은 작은 무대처럼 보이게 만든다.

### 컬러 방향

- 기본 UI는 중성 배경 위주로 간다.
- 포인트 컬러는 고양이와 잘 어울리는 따뜻한 크림, 세이지, 머스타드, 소프트 오렌지 계열이 좋다.
- 성공/기쁨은 노랑 또는 살구 계열, 오류는 탁한 빨강 또는 브릭 계열, 대기는 회청 계열처럼 감정과 톤을 연결한다.
- 지나치게 채도 높은 네온 컬러는 피한다.

### 펫 비주얼 원칙

- 펫은 픽셀아트 기반이지만, 실루엣은 멀리서도 읽혀야 한다.
- 얼굴 요소는 최소화하되 감정은 귀, 눈, 꼬리, 몸 기울기로 구분한다.
- 작은 움직임만으로도 살아 있는 느낌이 나게 설계한다.
- 기본 포즈는 장시간 봐도 질리지 않는 안정적인 형태여야 한다.

### 질감과 연출

- 앱 본체는 매끈한 현대 UI를 유지한다.
- 픽셀 텍스처는 펫과 일부 상태 배지 정도에만 제한적으로 사용한다.
- 반짝임, 먼지, 햇빛, 나비 같은 연출은 특별 상태에서만 약하게 사용한다.

### 하지 않을 것

- 전체 앱을 레트로 게임 UI처럼 만드는 것
- 너무 많은 색을 동시에 써서 산만해지는 것
- 펫 애니메이션이 채팅이나 작업 흐름보다 더 시선을 뺏는 것

### 패널 역할

- Top Bar:
  현재 세션 이름과 최소한의 전역 정보만 노출
- Left Rail:
  새 대화 생성, 세션 히스토리, 즐겨찾기, 펫 존재감을 동시에 담당
- Main Chat Surface:
  핵심 작업 공간, 모든 대화와 에이전트 수행 결과, 검색 흐름이 중심에 쌓임
- Right Context Panel:
  메모/할 일/일정/GitHub를 "현재 대화와 연결된 보조 정보"로 제공
- Bottom Strip:
  상태 메시지, 연결 상태, 모델 기동 상태

### 인터랙션 원칙

- 사용자는 기본적으로 중앙 패널에 머문다.
- 우측 패널은 항상 열려 있되, 카드 접기/펼치기로 밀도를 조절한다.
- 좌측 펫은 클릭 시 설정, 모델 상태, 간단한 quick prefs를 여는 진입점이 된다.
- 검색은 별도 전역 페이지보다 메인 채팅 플로우에서 자연스럽게 수행된다.
- 세션 히스토리는 좌측 rail에서 리스트로 탐색 가능해야 한다.
- 모바일보다 데스크톱 우선 구조로 설계한다.

### 대안 레이아웃

- 대안 A:
  오른쪽 패널 대신 하단 탭 패널을 두는 방식
- 대안 B:
  좌측 rail을 더 좁게 하고, 펫을 floating widget처럼 두는 방식

### 현재 추천

- 기본형은 3열 구조가 가장 안정적이다.
- 펫은 좌측 rail 하단 고정이 가장 무난하다.
- 설정과 모델 상태는 상단 바보다 펫 스테이지 쪽에 붙는 편이 더 자연스럽다.
- 메모/할 일/일정/GitHub는 페이지 전환보다 우측 컨텍스트 패널 탭이 더 잘 맞는다.
- 검색은 메인 채팅 기본 기능으로 본다.

### 애니메이션 규칙

- 기본 상태는 `idle_base`다.
- 감정 상태와 행동 상태는 조합 가능하게 설계한다.
- 긴 루프보다 짧은 루프를 간헐적으로 재생하는 방식이 좋다.
- 성공/실패 애니메이션은 짧고 명확해야 한다.
- 같은 애니메이션이 너무 자주 반복되면 피로하므로 쿨다운 개념이 필요하다.

### 제작 우선순위

1. `idle_base`
2. `idle_blink`
3. `working_type`
4. `curious_look`
5. `happy_bounce`
6. `error_freeze`
7. `sleepy_doze`

### 구현 메모

- 초기에는 각 상태를 독립 스프라이트 세트로 구현한다.
- 상태 전환 규칙이 안정되면 공통 프레임 재사용을 검토한다.
- 프레임 수보다 타이밍 설계가 더 중요하다.

## 19. Settings and Configuration UX

### 목표

- 사용자가 앱 안에서 주요 동작 설정을 직접 바꿀 수 있게 한다.
- `.env`를 수동 편집하지 않아도 LLM, GitHub, 프롬프트 관련 설정을 관리할 수 있게 한다.
- 설정은 개발자용 내부 옵션이 아니라, 실제 사용 가능한 제품 기능으로 제공한다.

### 설정 페이지에 포함할 항목

- LLM base URL
- LLM API path 또는 endpoint
- 기본 모델명
- temperature, max tokens 같은 주요 파라미터
- system prompt 또는 user prompt 편집
- GitHub API base URL
- GitHub token 입력
- 웹 검색 on/off
- 대화 히스토리 길이
- 펫 애니메이션 on/off 또는 강도
- 모델 자동 실행 / 자동 종료 옵션

### 프롬프트 설정 방향

- 단순 문자열 입력보다 "기본 프롬프트 복원" 기능이 필요하다.
- 프롬프트는 최소한 다음 레벨로 나누는 것이 좋다.
- chat prompt
- intent prompt
- tool planning prompt
- 필요하면 사용자 개인화 prompt

### UX 제안

- 설정 페이지는 사이드바에서도 접근 가능하지만, 기본 진입점은 고양이 스테이지 내부가 더 적합하다.
- 카테고리 탭 방식이 적합하다.
- 예시:
  - General
  - LLM
  - Prompts
  - Integrations
  - Appearance
  - Debug
- 민감 정보는 마스킹 처리하고, 저장 전에 연결 테스트를 지원하는 것이 좋다.
- 빠른 설정 몇 개는 고양이 스테이지 안에서 바로 조절할 수 있게 한다.

### 저장 방식 제안

- 우선순위는 "앱 내부 설정 저장소"를 기준으로 한다.
- 첫 버전은 SQLite `settings` 테이블을 활용하거나 별도 settings JSON 파일을 둘 수 있다.
- 앱 UI에서 저장한 값이 런타임에 바로 반영되는 구조가 좋다.
- `.env`는 개발/배포 초기값 용도로만 두고, 사용자 조작의 주 저장 경로로 쓰지 않는 편이 낫다.

### 주의점

- 프롬프트 편집은 잘못 수정하면 앱 품질이 크게 흔들릴 수 있다.
- 따라서 기본값 복원, 현재값 비교, 최근 변경 이력 정도는 고려할 가치가 있다.
- GitHub token 같은 민감 정보는 평문 노출을 최소화해야 한다.

## 20. Token Usage and Observability

### 목표

- 사용자가 현재 모델 사용량을 감으로 추측하지 않게 한다.
- 대화와 툴 사용이 토큰 비용에 어떤 영향을 주는지 보이게 한다.
- 디버깅과 품질 개선에 필요한 관측 가능성을 확보한다.

### 보고 싶은 지표

- 요청별 input tokens
- 요청별 output tokens
- 총합 tokens
- 최근 대화 기준 누적 사용량
- 단계별 사용량
- 예시:
  - intent classification
  - tool planning
  - chat response
  - tool narration

### UI 제안

- 기본 화면에서는 작은 usage badge만 노출
- 상세 값은 우측 패널 또는 Debug 탭에서 확인
- 설정 페이지 안에 "Model Usage" 섹션을 두는 것도 가능
- 사용자가 원하면 최근 20개 요청 정도의 사용량 로그를 볼 수 있게 한다
- 모델 상태 badge는 고양이 스테이지 안에서 자연스럽게 노출하는 편이 좋다

### 구현 고려사항

- 현재 LLM 백엔드가 usage 메타데이터를 반환하는지 먼저 확인해야 한다.
- 반환하지 않는다면:
  - llama.cpp 응답 메타데이터 활용 가능 여부 확인
  - 직접 토큰 추정기를 붙일지 검토
- 요청 단위로 어떤 호출이 발생했는지 trace를 남기는 구조가 필요하다.
- 응답 중단 시점에도 어디까지 토큰이 사용됐는지 부분 로그를 남길지 검토한다.

### 제품적 가치

- 사용자는 "왜 느린지", "왜 컨텍스트가 무거운지"를 이해하기 쉬워진다.
- 프롬프트 수정 효과를 사용량 관점에서도 확인할 수 있다.
- 나중에 로컬 모델을 여러 개 붙일 때 비교 지표로도 쓸 수 있다.
